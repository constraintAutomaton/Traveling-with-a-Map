\section{Related Work}\label{sec:related_work}

In this section, we review related work on \ac{LTQP}, \ac{RDF} data shapes, and source selection in decentralized querying.

\subsection{Link Traversal Query Processing}
\ac{LTQP} is a SPARQL querying paradigm that answers queries by exploring the Web using the \textit{follow-your-nose} principle~\cite{hartig2016walking}.
It belongs to the family of decentralized SPARQL querying paradigms.
\ac{LTQP} fundamentally differs from federated querying because the ``federation'' is formed during querying and it expands dynamically as the query is processed.
\rone{A federation is a set of queryable \ac{RDF} sources, typically SPARQL endpoints, that is fixed and known prior to query execution.}
Thus, many optimization techniques used in federated querying either do not work in the context of \ac{LTQP} or remain unexplored.
\ac{LTQP} also differs from querying \ac{LDF} interfaces~\cite{azzam2020smart,azzam2021wisekg,DBLP:journals/corr/HartigA16}, as \ac{LDF} operates over fragments of a known, local, finite \ac{KG}, whereas \ac{LTQP} dynamically discovers new, remote \acp{KG} during query processing.
In summary, \ac{LDF} methods such as \ac{TPF}~\cite{verborgh2016triple} focus on the efficient partitioning of a known dataset, while \ac{LTQP} focuses on the efficient discovery of an unknown dataset.
\rone{More generally, an \ac{LDF} interface publishes a dataset as a set of queryable fragments over the Web, balancing query-processing effort between the server and the client~\cite{verborgh2014web}.}


The main challenge of \ac{LTQP} is the Web's open-ended nature leading to large search spaces.
Completeness in \ac{LTQP} is defined by the traversal of a well-defined set of links~\cite{Hartig2012}.
\rone{A traversal is complete when it dereferences every link in this set, so that the query is answered completely over the subgraph those links induce; completeness in \ac{LTQP} is therefore relative to the set of reachable links rather than to the entire Web, whose search space is too large to traverse exhaustively.}
The first method used to define this set was the \emph{reachability criteria}~\cite{Hartig2012}, boolean functions that determine whether a given link should be dereferenced.
In practice, the query engine iterates over all triples in its internal data source and applies the reachability criteria to each \ac{IRI} appearing in those triples.
These criteria are defined internally by the engine, giving designers considerable freedom in how they are implemented and which links are dereferenced. 
However, there is currently no standard mechanism for users to specify them, nor for query engine developers to adopt a common approach.
Building on this, the theoretical query language \ac{LDQL}~\cite{hartigLDQL} was introduced, which separates the traversal definition from the query definition.
It provides a standard mechanism for query engines to define their traversal logic, while opening the possibility for users to provide a traversal policy alongside their queries.
Further advancements include the \ac{SWSL}~\cite{Bogaerts2021LinkTW}, which allows data providers to define how their \ac{DKG} should be traversed.
Inspired by \ac{SWSL}, traversal-based querying has utilized the \ac{LDP} and the Type Index specification~\cite{Taelman2023}.
\ac{LDP} traversal follows all links within a data space, while Type Index traversal uses mappings from \ac{RDF} types to relevant resources~\cite{solidTypeIndexes}, allowing queries to prioritize implicitly relevant data sources.
Link prioritization has also been studied, however, it has been shown to not improve query execution time~\cite{hartig2016walking}, even in \acp{DESP}~\cite{eschauzier_iswc_research_linkprioritization_2025}.
These contributions are centered on guiding the engine in selecting links to follow in a discovery process.
However, they do not explicitly address the restriction or pruning of links after the discovery process based on information acquired during traversal.
\rone{We distinguish discovery from pruning as assertion differs from negation: a discovery criterion expresses that a link should be explored, whereas a pruning criterion expresses that it should not, and the latter takes precedence, so a pruned link is not followed even when a discovery criterion would select it.
Discovery builds the search domain of an \ac{LTQP} query, whereas pruning carves holes into that domain.
Although both can be described as retaining a subset of links, only inclusion is sound under the open-world assumption of the web, since a missing link is no evidence that relevant data is absent; excluding links soundly requires closed-world knowledge about a region of the web.}
Such pruning could significantly reduce the query search domain when information about the \ac{DKG} data model is available.
For instance, the structural properties of a subweb could inform the query engine that certain web sections follow a specific data model, allowing a set of \acp{IRI} to be pruned from those selected during discovery.
In contrast, when \ac{LTQP} models \acp{DKG} as Linked Open Data, the web is not divided into subsections with structural properties; thus, data model information cannot be inferred.
To the best of our knowledge, no prior work has explored the use of a pruning mechanism to optimize \ac{LTQP}, and it is this research gap that the present study aims to address.

\subsection{RDF Data Shapes}
\ac{RDF} data shapes (in this paper, we also refer to them as shapes) are used for validating, describing, and communicating data structures, as well as generating data and driving user interfaces~\cite{Gayo2018a,Gayo2018}.
The two most well known \ac{RDF} data shape formalisms are \ac{SHACL}~\cite{Gayo2018b} and \ac{ShEx}~\cite{Gayo2018}.
%Both describe RDF data but differ in focus: ShEx emphasizes graph structure, while SHACL targets constraints.
For common use cases, they are equally expressive and interchangeable~\cite{Gayo2018c}.
\ac{RDF} data shapes have already been used in the literature for querying centralized \acp{KG}~\cite{kashif2021, delva2023}.
Shape Trees~\cite{shapetreesShapeTrees} are an index structure for validating and organizing \acp{DKG}; \rone{however, to the best of our knowledge, they have not been used for query optimization, and their \emph{virtual hierarchy}~\cite{shapetreesShapeTrees} makes it challenging for a query engine to efficiently capture the relationship between a resource \ac{IRI} and its corresponding shape.
Beyond this conceptual mismatch, Shape Trees were not yet practical to build upon at the time of this study: the specification is not widely adopted, and its supporting documentation and tooling were not sufficiently mature or stable.
We therefore conduct our investigation using the Shape Index specification~\cite{tam2024opportunitiesshapebasedoptimizationlink} to map shapes to \acp{KG}.
Importantly, our findings are not tied to this particular summary: our approach relies in essence on a mapping between shapes and sets of \acp{IRI}, so any structure providing such a mapping---including a more mature Shape Trees---could serve as the underlying summary instead.}
Additionally, automatic generation of \ac{RDF} data shapes from \acp{KG}~\cite{fernandez2023extracting} and shape-based data integration~\cite{LabraGayo2023} have been studied and can support shape-based summary approaches for \acp{DKG}.

\subsection{Source Selection}
Source selection is a crucial challenge in decentralized querying~\cite{hose2012towards, Harth2010}.
\rone{It is the process of determining, before or during query execution, which of the available data sources can contribute to the result of a query, so that sources that cannot are not accessed.}
Link pruning in \ac{LTQP} is closely related to source selection, as it can be viewed as a dynamic form of source selection.
Methods such as basic statistics on triple counts, \ac{VoID} descriptions, and histogram techniques have been explored in the context of federated querying~\cite{hose2012towards, Harth2010, Montoya2017}.
\rone{A \ac{VoID} description is an \ac{RDF} document that summarizes a dataset, reporting, among other things, its total number of triples and the set of predicates it uses. Figure~\ref{fig:void} shows such a description for the \texttt{sw:posts} dataset of our running example.}

However, most of those source selection methods face the limitation of assuming a small number of data sources~\cite{Harth2010}, leaving their suitability for \ac{LTQP} uncertain.
Bloom filters~\cite{dia2018fast} are also a mechanism that has shown success for federated \acp{DKG}, yet in the context of \ac{LTQP}, it has been show that bloom filters have little effect on performance~\cite{Hanski2024}.
Schema-based indexing using ontologies~\cite{Stuckenschmidt2004} has also been explored for source selection of SPARQL queries.
It has been shown that this approach is sensitive to the high reuse of vocabulary terms in \ac{RDF}~\cite{Harth2010}, which is exacerbated in the context of \ac{LTQP}.
The use of implicit \ac{RDF} schemas for query optimization has been explored through the concept of characteristic sets~\cite{Neumann2011CharacteristicSA, Meimaris2017ExtendedCS, Montoya2017}.
However, their applicability to \ac{LTQP} has not been investigated, and they assume that the entire dataset resides in memory, which is not the case for \ac{LTQP}.
